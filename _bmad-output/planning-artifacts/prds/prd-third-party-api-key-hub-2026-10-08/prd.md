## 产品目标

内部系统通过统一的品牌或店铺身份获取第三方平台 API 凭据，减少各业务系统重复处理授权回调、凭据生命周期和店铺归属映射的工作。

首期接入 TikTok Shop，支持店铺授权和手工导入 API Key／Token。有权限的调用者仅在服务所在 Linux 主机通过 CLI 获取完整明文凭据，直接用于第三方 API 调用。后续接入用户自建的 Vaultwarden 密码管理平台，在密钥更新后自动推送，平台内的查看权限由 Vaultwarden 决定。

## 首期与后续边界

首期包含 FR-1 至 FR-12，以及 Go Linux 常驻服务和 CLI 的交付。授权回调的网络可达性独立设计，不能由凭据查询／导出仅限可信内部环境推定。

首期取密仅限服务所在 Linux 主机上的 CLI。后续 Vaultwarden 集成不属于 FR-1 至 FR-12 的首期验收，不阻塞首期交付。

首期运维管理全部通过 CLI 提供，不建设 Web 管理界面；第三方平台授权页面及本中心授权回调入口不属于 Web 管理界面。

首期撤销仅在本中心停用凭据；第三方平台侧授权撤销由运维另行处理，不属于本中心的自动撤销能力。

以下能力已确认归入后续范围：

- CLI 的钉钉身份验证。
- 更多平台适配器和凭据代理调用。
- 多租户、角色权限和更细粒度的终端授权策略。
- 商品、订单、广告等第三方业务数据同步。
- CLI 独立分发到用户终端及相关终端授权、敏感字段控制和分发渠道。
- 密钥更新后自动推送到用户自建的 Vaultwarden 密码管理平台，由 Vaultwarden 管理其平台内的访问与查看权限。

### 后续 Vaultwarden 同步方向

- **PF-1 自动推送更新**：本中心管理的密钥更新后，自动推送到自建 Vaultwarden 中对应的密码管理条目；该能力属于后续范围，未指定实施版本或日期。
- **PF-2 平台查看权限**：凭据进入 Vaultwarden 后，谁可以访问或查看由 Vaultwarden 的权限配置决定。本中心不另行复制 Vaultwarden 的查看权限规则。
- **待设计**：同步覆盖哪些凭据与更新事件、条目与业务对象的映射、首次同步、同步时限、失败重试、乱序更新、Vaultwarden 中手工修改的冲突处理，以及撤销和删除如何传播，见 Q-11。
- 集成方式与同步账户的技术方案见交接补充；目前未核实具体接口，也未决定以 Vaultwarden 替换本中心的生产密钥存储服务。

## 使用者与任务

- **集成运维人员**：登记平台 App，发起店铺授权，维护店铺映射，检查凭据状态、失效时间和归属，处理失效授权。
- **内部业务系统和自动化脚本**：按品牌、内部店铺或外部店铺查询可用凭据，用稳定 JSON 输出接入自动化处理；首期取密须在服务所在 Linux 主机执行 CLI，远程系统不直接从本中心取密。

首期交付界面是 Linux 常驻服务与 CLI。登记平台 App、维护映射、手工导入凭据、发起授权及其他运维管理操作均通过 CLI 提供，不建设首期 Web 管理界面。第三方平台要求的授权登录和同意操作仍在平台页面完成，由常驻服务承接回调。

本稿按内部工具的能力组织需求，不虚构具名用户旅程。下面的任务链来自已确认能力，用于检查需求覆盖；管理入口及产品行为已确认，具体命令参数与字段编码交给 CLI 设计：

- **接入与归属登记**：登记平台 App，建立外部店铺、品牌、内部店铺的关联，取得并保存与平台 App 或安装授权对应的凭据。
- **业务取密**：有权限的内部调用者按品牌或店铺定位凭据，通过 CLI 获取 JSON 结果，再直接调用第三方 API；第三方业务数据同步属于后续范围。
- **授权维护**：系统自动刷新支持刷新的凭据，运维人员检查状态和有效期并处理失效授权；刷新失败时仍有效的旧凭据可继续返回，过期或撤销后拒绝返回。未知有效期按 FR-6 处理；刷新时机与平台机制见 Q-6、Q-7。

## 术语与关系

| 术语 | 定义与约束 |
| --- | --- |
| 第三方平台 | 提供授权和业务 API 的外部平台，首期为 TikTok Shop。 |
| 平台 App | 登记于第三方平台的应用，与外部店铺通过安装授权建立多对多关联。 |
| 外部店铺 | 第三方平台上的店铺；每个外部店铺只能属于一个品牌。 |
| 品牌 | 外部店铺的业务归属；可对应多个外部店铺，与内部店铺双向一对一。 |
| 内部店铺 | 内部系统中的店铺，与品牌双向一对一。 |
| 安装授权 | 平台 App 与外部店铺的授权关联，每个安装授权的凭据状态独立可追踪。 |
| 凭据 | 用于调用第三方 API 的 API Key／Token，包括平台 App 级和安装授权级凭据。具体类型由平台能力决定。 |
| 可信内部环境 | 首期取密范围已具体限定为服务所在 Linux 主机上获授权运行 CLI 的环境，不等同于任何内网调用者均获授权。 |
| 调用者 | 发起 CLI 查询的内部业务系统、自动化脚本或运维人员；可查询的范围及调用资格验证见 Q-4。 |
| 撤销 | 在本中心停用目标凭据，拒绝后续取密；不自动撤销第三方平台授权，平台侧操作由运维另行处理。本地撤销不能宣称凭据在第三方平台已失效。 |
| Vaultwarden | 用户自建的密码管理平台；后续接收本中心在密钥更新后自动推送的凭据，其平台内的访问和查看权限由 Vaultwarden 决定。 |

## 功能需求基线

FR-1 至 FR-12 保留原编号，供架构和 Story 引用。验收条件来自定稿简报及用户后续确认；所有功能遵守 NFR-1。技术交接事项不代表平台能力已经核实，须在对应 Story 编写前落实。

### 平台登记与归属映射

#### FR-1 平台与 App 登记

运维人员可以通过 CLI 登记第三方平台及其平台 App；首期支持 TikTok Shop。

**验收条件**：

- 已登记的 TikTok Shop 平台 App 可被后续安装授权和凭据关联引用，并能明确识别其所属平台。
- 平台与平台 App 的登记由 CLI 完成，无须使用本中心的 Web 管理界面。
- 必填平台、本中心 App 标识、平台侧 App 标识，显示名称可选；本中心 App 标识全局唯一，平台与平台侧 App 标识的组合唯一。缺少必填字段或重复登记时拒绝操作。
- 平台要求的授权配置与秘密字段由适配器核实；缺少所需配置时明确反馈，不假设各平台字段一致。命令语法交给 CLI 设计。

#### FR-2 安装授权关联

系统支持平台 App 与外部店铺的多对多关联，并独立追踪每个安装授权的凭据状态。

运维人员通过 CLI 查询安装授权的关联与状态；关系创建由授权回调或确认的手工导入流程完成。

**验收条件**：

- 一个平台 App 可以关联多个外部店铺，同一个外部店铺也可以关联多个平台 App。
- 可以分别查询各安装授权的关联对象与凭据状态，状态不会因另一份安装授权变化而被混为同一个状态。
- **已确认**：同一平台 App 与外部店铺再次授权成功后，更新现有安装授权与当前凭据，不新增供正常查询选择的独立授权版本；保留操作历史，正常查询只返回当前凭据。
- 操作历史不得记录真实凭据，继续遵守 NFR-1；历史字段与保留期限见 Q-8。

#### FR-3 外部店铺归属

系统维护外部店铺与品牌的映射，校验一个外部店铺只能属于一个品牌；一个品牌可以对应多个外部店铺。

运维人员通过 CLI 建立、查询和维护外部店铺与品牌的映射；通过唯一性校验的变更或解除操作成功后立即生效，已有凭据可以保留，取密依据变更后的完整归属链判断。

**验收条件**：

- 一个品牌可以关联两个或更多外部店铺。
- 将同一个外部店铺同时归属到两个品牌的操作不能成功形成违规关系。
- 按品牌查询时，凭据的外部店铺归属可追溯到该品牌。
- 未绑定品牌的外部店铺不能进入可取密状态；完成品牌映射前，按该店铺查询不得返回明文凭据。
- 映射解除后，保留的凭据也不得绕过完整归属链限制；完整映射恢复后，仍须满足凭据有效性和调用资格等取密条件。
- 使用外部店铺与品牌的稳定标识管理映射，名称仅辅助展示；唯一性冲突时拒绝整个变更、原映射不变，不自动抢占或改绑。

#### FR-4 内部店铺映射

系统维护品牌与内部店铺的双向一对一映射，并校验两端归属唯一性。

运维人员通过 CLI 建立、查询和维护品牌与内部店铺的映射；通过唯一性校验的变更或解除操作成功后立即生效，已有凭据可以保留。

**验收条件**：

- 已建立的品牌与内部店铺映射可从两端定位到同一关联。
- 将一个品牌同时关联两个内部店铺，或将一个内部店铺同时关联两个品牌的操作，均不能成功形成违规关系。
- 未建立内部店铺映射的品牌，其外部店铺凭据不能进入可取密状态；完成品牌与内部店铺映射前，按该品牌、内部店铺或其外部店铺查询不得返回明文凭据。
- 映射变更后，按新归属链判断取密；旧关联或缓存不得继续允许通过已解除的归属关系取密。完整归属链缺失期间禁止取密。
- 使用品牌与内部店铺的稳定标识管理映射，名称仅辅助展示；唯一性冲突拒绝整个变更、原映射不变，不自动抢占或改绑。缺少完整映射使用 FR-10 的稳定错误类别，并发和缓存失效机制交给架构。

### 凭据获取与生命周期

#### FR-5 店铺授权

运维人员通过 CLI 发起 TikTok Shop 店铺授权，在第三方平台页面完成所需的授权登录和同意，常驻服务通过授权回调完成凭据获取、保存和关联更新；回调处理必须安全、幂等。

**验收条件**：

- 按已核实的平台授权流程完成一次授权后，可以定位取得的凭据及其对应的平台 App、外部店铺和安装授权。
- 授权发起和授权结果查询由 CLI 提供，本中心无须建设 Web 管理界面；平台页面授权与常驻服务回调仍为完整流程的一部分。
- 同一次回调被重复处理，不会生成重复的当前关联或破坏已完成的关联。
- 同一 App／外部店铺通过一次新的授权成功取得凭据后，更新现有安装授权；再次处理该次回调不新增当前授权版本，正常查询不会返回被替换的旧凭据。
- 再次授权未成功时，不将未完成取得或保存的凭据视为已完成更新；已有凭据仍须按实际有效性和撤销状态判断是否可返回。
- 无法验证来源或关联对象的回调不能完成凭据保存与关联更新。
- 平台实际协议、回调校验、部分失败恢复与回调可达性由平台接入设计者在对应 Story 编写前核实，见 Q-7；授权成功不等同于取密权限授予，也不自动解除已有本地停用。

#### FR-6 手工导入

运维人员可以通过 CLI 手工导入 API Key／Token，与店铺授权获取凭据并行提供。运维人员确认可用后允许直接取密，平台验证是可选操作，不作为所有手工导入凭据保存和查询的前置条件。

**验收条件**：

- 运维人员可以通过手工导入取得凭据记录，无须先完成店铺授权。
- 导入时必须明确凭据归属：App 级凭据绑定平台 App；店铺级凭据绑定平台 App 与外部店铺的组合。缺少所需归属时拒绝导入，不保存无归属凭据等待后续绑定。
- 导入后能区分凭据属于平台 App 级还是安装授权级，并定位对应的关联对象；绑定 App／外部店铺不替代取密所需的完整品牌与内部店铺归属链。
- 除所需归属外，凭据类型与凭据值必填；缺少任一必填内容时拒绝导入。有效期和刷新凭据为可选字段，并按平台支持情况校验；未填写有效期不推定为永不过期，沿用“有效期未知”与运维确认规则；未提供刷新凭据不推定该凭据可刷新。
- 同一目标已有同类型凭据时，运维人员必须明确指定“替换”才允许覆盖；未明确指定时导入失败，已有凭据及其状态保持不变，不自动覆盖或新增正常查询的候选版本。
- 明确指定替换后，成功导入的新凭据成为该目标该类型的当前凭据；替换未成功时不误报完成，也不将未完成保存的新凭据视为当前凭据。取密仍须满足完整归属链、可用性和调用资格规则。
- 手工导入凭据的有效期未知时，只要运维人员已确认当前值可用，即可正常取密；状态必须标记为“有效期未知”。确认与验证证据绑定所适用的秘密值版本；明确替换后新值不继承旧确认或验证结果，同次导入可显式确认新值。
- 平台验证为可选操作；运维确认、验证未完成和明确失效按 FR-7 区分，取密继续遵守 FR-8、FR-11 的有效性、本地停用及完整映射限制。
- 导入成功和失败的处理均遵守 NFR-1。
- 手工导入及其结果查询通过 CLI 提供，同时支持隐藏凭据值的交互输入和从标准输入读取的非交互脚本模式；两种模式均须遵守 NFR-1，不回显输入的凭据值，导入结果不回传凭据值，不将其写入日志、审计、告警或错误响应。交互提示使用标准错误，标准输出保留该次操作的 JSON 结果。
- **交给 CLI 与接入设计**：字段名称、输入格式、隐藏输入机制及平台支持校验，见 Q-5、Q-7；不能将“未验证”与“平台已确认失效”混为一类。

#### FR-7 凭据保存与验证

系统保存平台 App 级和安装授权级凭据，提供可查询的状态、有效期与验证结果。手工导入凭据允许由运维确认可用，平台验证为可选能力；其具体接口与支持范围由平台接入设计核实。

**验收条件**：

- 可以区分平台 App 级和安装授权级凭据，查询其状态与有效期信息。
- 每份凭据的验证结果归属到对应目标、类型及秘密值版本；换值不继承旧值验证证据，迟到的旧版本结果不能覆盖新值。暂时故障保留同版本已有确定证据并另记本次未完成尝试。
- 运维确认可用与平台验证成功是不同的结果；未执行平台验证不能伪装成成功，也不构成拒绝已获运维确认的手工导入凭据的唯一原因。
- 凭据保存和验证过程遵守 NFR-1；验证失败的诊断不返回真实凭据。
- 验证结果区分明确失效与验证未完成：网络超时或平台暂时故障记录为“验证未完成”，既不伪装为验证成功，也不覆盖原可用状态；明确确认失效时停用并拒绝取密。验证未完成不使原不可用、过期或已本地撤销的凭据恢复可用。
- 已过期或已撤销的凭据不能作为可用凭据从查询／导出结果中返回；刷新失败本身不等同于旧凭据失效，仍须检查旧凭据是否有效。
- 手工导入的未知有效期按 FR-6 处理；明确失效后的停用适用于所有凭据。
- 业务调用明确发现失效时，由获 manage 资格的调用者通过服务主机 CLI 以目标、类型和使用时的 expected_generation 标记该版本失效；匹配当前版本才停用，旧值报告不能停用后来刷新的新值，冲突按稳定输入错误拒绝且状态不变。运维主动停用当前目标是独立操作。标记结果可查询并纳入 FR-12 审计，版本引用不含秘密。首期不新增远程失效上报接口，不由本中心代理业务 API。
- 验证时间与状态编码由 CLI 契约设计细化；平台验证接口、支持范围以及暂时故障与明确失效证据的分类由接入设计核实，见 Q-7。

#### FR-8 凭据刷新与撤销

系统自动维护支持刷新的凭据，并提供撤销能力。刷新失败时，旧凭据仍有效则继续允许返回；凭据过期或撤销后拒绝返回。平台实际能力与手工导入凭据是否支持刷新按接入设计核实，不能推定所有 API Key／Token 都可自动刷新。

运维人员通过 CLI 查询维护状态和发起本地撤销；撤销只在本中心停用目标凭据，第三方平台授权由运维另行处理。自动刷新由常驻服务执行，不要求 CLI 持续运行。

**验收条件**：

- 对支持刷新的凭据提供自动刷新；本地撤销不依赖第三方平台是否支持撤销接口，操作后可查询目标凭据的停用状态。
- 本地撤销成功后立即拒绝返回目标凭据，不调用第三方平台撤销接口，不宣称平台授权已解除。
- 已本地停用的凭据不能因后台刷新、验证成功或映射恢复而自动恢复取密；运维重新授权或明确替换导入后，须显式确认恢复取密，并重新满足可用性、完整映射和调用资格条件。恢复资格须持久化证明停用后有合格替换/重新授权，不能仅比较 generation 或从可缺失的审计推断；刷新可保留已有资格但不能创建资格，再次停用清空资格。确认/恢复明确指向当前版本，具体入口交给 CLI 设计，调度与并发处理必须保留本地停用决定。
- 刷新成功后，可查询更新后的可用凭据与状态；旧凭据的轮换和有效性依据平台实际规则处理，不能未经核实推定仍可使用。
- 刷新失败时，如果旧凭据仍有效且未被撤销，正常查询允许继续返回该旧凭据；刷新失败不能延长其有效期。
- 旧凭据已过期或已撤销时，查询／导出不返回其明文内容，并以 FR-10 的安全错误契约表达不可用结果。
- 操作结果可归属到具体凭据或安装授权；无法通过平台接口执行的能力必须在接入设计中明确，不得宣称平台侧操作已成功。
- 刷新和撤销过程的诊断遵守 NFR-1。
- 再次授权沿用 FR-2、FR-5；手工导入字段与未知有效期沿用 FR-6。本地停用限制适用于导入与授权取得的凭据，历史沿用 FR-12。
- **交给接入与架构设计**：刷新提前量、调度与重试、并发更新、平台 Token 轮换和失效判定，见 Q-7；这些技术参数尚未指定。

### 内部查询与审计

#### FR-9 按业务归属查询

有权限的调用者可以在服务所在 Linux 主机通过 CLI 按品牌、内部店铺或外部店铺查询用于第三方 API 调用的完整凭据。

**验收条件**：

- 对已建立完整映射的测试数据，分别按品牌、内部店铺和外部店铺查询，能按对应的归属关系定位凭据。
- 只有完成“外部店铺 → 品牌 → 内部店铺”完整归属链的凭据才可进入正常取密结果；任一映射缺失时，查询不得返回明文凭据。
- 查询返回的每份凭据具有可辨认的归属，不会把其他品牌或店铺的凭据标记为目标对象的凭据。
- **已确认**：按品牌、内部店铺或外部店铺查询匹配多个平台 App 时，调用者须指定平台 App 后才能取得对应凭据；未指定时不返回明文凭据，也不自动选择默认 App 或返回所有 App 的凭据。
- 当查询目标只匹配一个平台 App 时，系统可以自动使用该唯一 App；不要求调用者重复指定。
- 指定平台 App 后，查询结果仅包含该 App 在目标品牌或店铺范围内对应的凭据，不混入其他 App 的凭据。
- **已确认**：指定平台 App 后，按品牌或内部店铺定位的目标仍匹配多个外部店铺时，调用者须进一步指定外部店铺；未指定时不返回这些店铺的明文凭据列表，也不自动选择一个外部店铺。
- 当所选 App 下只匹配一个外部店铺时，系统可以自动使用该唯一店铺；不要求调用者重复指定。
- 指定外部店铺后，只返回同时属于所选 App、外部店铺和查询目标归属范围的凭据；外部店铺不属于目标品牌或所选 App 时不能返回其凭据。
- 刷新失败但旧凭据仍有效时可以返回旧凭据；已过期或已撤销的凭据不返回明文。组合中任一必需凭据缺失、过期、停用或因其他原因不可用时，查询整体失败，不输出任何明文凭据，也不返回仍可用的部分凭据。
- 同一 App／外部店铺再次授权成功后，正常查询仅返回更新后的当前凭据，不提供旧授权版本的取密选择。
- **已确认**：查询店铺凭据时，一并返回调用第三方 API 所需的对应平台 App 级凭据（如 App Key／Secret）和店铺 Token，无须再独立查询 App 级凭据；返回范围限定为所选 App 与店铺的业务 API 调用所需凭据；仅用于刷新或管理授权的凭据（如 refresh token）由本中心内部使用，不随正常查询返回。
- 无匹配项、须指定 App／店铺及必需凭据不可用等结果按 FR-10 的稳定错误类别表达；唯一匹配自动解析不改变其他取密条件。

#### FR-10 JSON 明文结果

首期凭据查询输出稳定、机器可读的 JSON，包含业务 API 调用所需的完整明文凭据及确认的元数据。成功结果按归属信息、调用凭据、状态与有效期三组组织，字段名称和平台差异由 CLI 契约设计确定。

**验收条件**：

- 成功查询的正常输出能被标准 JSON 解析器读取，返回所需的完整凭据值，不以掩码或占位符替代真实查询结果。
- 测试与文档使用虚构凭据检查值是否完整，禁止将真实凭据用作测试样本。
- 失败响应遵守 NFR-1，不包含真实凭据。
- 组合中任一必需凭据不可用时，整体查询返回 `{"error":"...","message":"..."}`，退出码非零；包括仍可用的部分凭据在内，标准输出不得包含任何明文凭据。
- 店铺取密成功结果同时包含对应 App 级调用凭据与店铺 Token，并能够区分二者的归属；平台所需字段由接入设计核实，不混入其他 App 的凭据。
- 正常查询只返回业务 API 调用所需凭据，不返回仅用于刷新或管理授权的凭据（如 refresh token）；App Secret 若为业务调用所需仍按上述规则返回，不能将所有 App 级秘密都误归为管理凭据。
- 成功和失败结果均以 JSON 输出：标准输出只包含该次操作的 JSON 结果，标准错误只用于诊断，不把诊断文字混入标准输出。
- 成功使用退出码 `0`，首期所有失败统一为 `1`；失败时标准输出仍为机器可解析的 JSON 错误对象，具体原因由 `error` 判断。
- 失败标准输出统一使用简化 JSON 错误对象：`{"error":"...","message":"..."}`；`error` 用于机器识别错误类别，`message` 提供不含敏感信息的安全说明。
- 成功结果同时包含平台、App、外部店铺、品牌、内部店铺标识，以及各具体凭据的类型、非敏感 generation、状态和有效期；type 与 generation 对应本次值的同一快照，供版本失效报告引用。有效期未知明确标识，不推定永不过期。
- `error` 使用稳定类别，至少区分输入错误、对象不存在、须指定 App／店铺、归属不完整／不匹配、无权限、必需凭据缺失、过期、停用及内部故障。编码与多原因时的优先级由 CLI 契约设计确定。
- 同一主版本保持已有字段、类型和含义稳定，只在声明的非敏感元数据位置增加兼容的可选字段；旧 CLI 忽略允许位置的未知元数据并按已验证字段重建输出。未知秘密类型/字段、重复项及错误对象夹带值仍拒绝；请求严格校验不放宽。破坏性调整升级主版本。
- 具体字段名与错误编码由 CLI 设计者在对应 Story 编写前落实；各平台字段的业务调用、刷新和管理用途由接入设计者核实。

#### FR-11 查询范围与访问控制

首期凭据查询／导出仅允许在服务所在 Linux 主机运行 CLI，调用资格通过受控 Linux 系统账户权限管理，不提供远程取密入口。具体账户与运行权限配置由架构设计确定。

**验收条件**：

- 未获查询权限的调用者不能取得明文凭据；系统不向其披露超出权限范围的对象信息。可访问内部网络不等同于获查询权限。
- 获授权的 Linux 系统账户可以在服务主机执行 CLI 取密；未获授权的系统账户不能通过同一 CLI 取得明文凭据。
- 部署验收必须验证其他主机不能直接调用本中心进行凭据查询／导出；内网可达或公网可达均不构成远程取密资格。
- 第三方授权回调入口的可达性不能自动扩大凭据查询／导出的访问范围。
- **已确认**：首期采用服务主机本地 CLI 的访问边界，后续 Vaultwarden 中的查看权限由 Vaultwarden 决定；这不改变首期本地 CLI 的权限管理。
- **已确认**：未完成外部店铺、品牌和内部店铺完整归属映射时，任何查询路径均不得返回该店铺的明文凭据；CLI 仍应按确认的 JSON 错误契约返回失败结果。
- **交给架构**：获授权的 Linux 账户、CLI 与凭据存储的权限配置、账户资格撤销和审计身份记录；首期不引入远程调用者访问凭证方案。见 Q-4。

#### FR-12 基础访问审计

系统提供基础访问审计，覆盖所有凭据相关操作：成功和失败的查询、导入、授权、验证、刷新、本地撤销、失效标记、显式恢复，以及 App 登记和归属映射变更。

**验收条件**：

- 实施完成后，可以检索确认范围内的访问审计事件，并按确定的字段检查事件结果。
- 审计内容遵守 NFR-1，不包含真实凭据。
- 成功和失败事件均应记录，失败事件不因没有返回明文凭据而省略；审计记录本身不得成为 CLI 标准输出中的额外非 JSON 文本。
- **已确认**：审计范围覆盖查询、导入、授权、刷新、撤销和映射变更的成功与失败事件。
- 审计记录至少保留一年；审计写入失败不阻止原操作，但必须记录不含真实凭据的系统告警，供运维发现审计降级或丢失风险。
- **已确认最小字段**：时间、发起操作的 Linux 系统账户、操作类型、目标对象引用、操作结果、错误类别和操作 ID；目标对象只记录平台 App、外部店铺、安装授权、品牌或内部店铺等非敏感标识，不记录任何凭据值。
- 审计存储边界、字段编码和告警通道交给架构设计者在审计 Story 编写前落实，见 Q-8。

## 跨功能质量要求

- **NFR-1 凭据保密**：真实凭据不得进入源码、Git、日志、测试数据、审计记录、系统告警或错误响应。正常查询明文返回不放宽这些约束。
- **NFR-2 关系完整性**：外部店铺归属和品牌／内部店铺映射满足上述唯一性约束；只有完整归属链存在时才允许凭据进入明文查询结果。映射变更或解除成功后立即影响后续查询，旧关联或缓存不得继续允许取密；唯一性冲突拒绝整个变更，保留原映射；错误编码交给 CLI 设计。
- **NFR-3 回调可靠性**：授权回调安全、幂等地完成凭据保存与关联更新；重试和失败恢复验收条件待平台接入设计明确。
- **NFR-4 平台扩展性**：新增平台适配器不要求修改核心外部店铺、品牌、内部店铺和安装授权模型。
- **NFR-5 脚本兼容性**：CLI 标准输出只提供 JSON；成功退出码 0，首期失败统一 1，失败对象为 `error` 与 `message`。同一主版本保持已有字段、类型和含义稳定，仅增加兼容的可选字段；破坏性调整升级主版本。诊断与提示使用标准错误。
- **NFR-6 可部署性**：提供可复现的 Linux 构建和打包命令及 `systemd` 配置；生产环境支持专用密钥管理服务。

## 成功判据基线

使用虚构凭据验证功能与错误路径。真实 TikTok Shop 接入所需的受控环境由平台接入设计确定；以下判据不表示现有实现已通过验收。

### SM-1 安装授权独立性

使用至少两个 App 和两个外部店铺验证双向多对多关系，每个安装授权状态独立。缺少登记必填字段、重复本中心 App 标识或重复平台／平台侧 App 标识时，登记失败且已有记录不变。对应 FR-1、FR-2、FR-7。

### SM-2 归属唯一性

- 验证品牌可关联多个外部店铺，外部店铺只能归属一个品牌，品牌与内部店铺双向一对一；冲突拒绝整个变更，原映射不变。
- 已有凭据时解除任一映射，凭据可保留但任何查询路径均禁止取密；恢复完整链且其他条件满足后才可取密。
- 变更为另一完整链时新归属立即生效，旧归属和缓存不再允许取密；稳定标识不受显示名称变化影响。

对应 FR-3、FR-4、FR-9。

### SM-3 授权获取

CLI 发起授权、平台页面登录同意、服务处理回调、CLI 检查结果，全程无须本中心 Web 管理界面。重复回调不生成重复当前关联；再次授权更新现有授权，正常查询只返回当前凭据。失败不误报更新，历史不含秘密；来源校验按核实的平台规则验收。对应 FR-2、FR-5、FR-9。

### SM-4 手工导入与维护

- **输入与归属**：隐藏交互和标准输入均可导入，输入值不回显，结果／诊断／审计／告警无凭据值，提示不污染 JSON。App 级绑定 App，店铺级绑定 App 与外部店铺；缺少归属、类型或值时导入失败且不保存无归属凭据。省略有效期或刷新凭据不妨碍其余条件满足的导入，不误报有效期或刷新能力；缺少品牌／内部店铺映射仍禁止取密。
- **覆盖**：未指定替换时失败且原凭据与状态不变；明确替换成功后查询使用新当前凭据，替换失败不误报成功。
- **可用与验证**：确认A后替换B未确认，B不得继承A的确认或验证；未知有效期经当前版本运维确认后可取密并标记未知；运维确认与平台验证结果可区分。验证超时或平台暂时故障标记未完成，保留原可用状态，不恢复原已过期或停用凭据。明确发现失效后停用，包括通过本地 CLI 标记业务发现的失效。
- **刷新**：支持刷新的凭据自动刷新；刷新失败但旧凭据仍有效且未停用时可返回，已过期或停用后拒绝。
- **版本失效报告**：查询旧值→刷新新值→报告旧generation失效，新值不得停用；匹配当前generation的报告可停用，运维主动停用独立生效。
- **停用与恢复**：仅刷新后显式恢复仍拒绝，明确替换/重新授权产生事务内资格；替换后刷新保留资格，再次停用清空资格，重启后规则一致。本地撤销立即拒绝取密，不调用平台撤销接口、不宣称平台授权解除。后台刷新、验证成功及映射恢复不解除停用；重新授权或明确替换导入后，未经显式确认仍不能取密，确认后重查有效性、完整映射与权限。

对应 FR-6、FR-7、FR-8；输入格式由 CLI 设计确定，平台验证按核实能力验收。

### SM-5 业务取密

- **归属与选择**：按品牌、内部店铺、外部店铺查询的归属正确；任一映射缺失时错误 JSON 无明文。唯一 App／店铺自动使用，多 App／店铺须显式指定；未指定或指定范围外对象时不返回凭据。
- **组合与完整性**：同一次查询完整返回对应 App 调用凭据和店铺 Token，不混入其他 App，不返回 refresh token 等仅用于刷新或管理的凭据。任一必需 App 凭据或店铺 Token 缺失、过期或停用时整体失败，错误响应不含仍可用部分的凭据值，诊断与审计也无秘密。
- **契约**：标准 JSON 解析与值比较验证明文完整性；成功为三组结构，含全部归属标识与每份凭据的类型／状态／有效期，未知有效期明确标识。成功退出码 0，所有错误场景为 error/message JSON 和退出码 1，错误覆盖确认类别，标准错误不污染标准输出。同一主版本不破坏字段、类型与含义；旧CLI接收允许位置新增可选非敏感字段成功，不透传未知字段；未知秘密/重复项/错误响应夹带值仍失败。

对应 FR-9、FR-10；再次授权的当前凭据检查见 SM-3，停用恢复见 SM-4。

### SM-6 访问边界与审计

获授权 Linux 账户可在服务主机取密；未获授权账户和其他主机不能直接查询／导出。确认范围的成功／失败事件可检索，含时间、Linux 账户、操作类型、非敏感目标引用、结果、错误类别和操作 ID，无凭据值，至少保留一年。模拟审计写入失败，原操作完成且产生无秘密的系统告警。对应 FR-11、FR-12；存储与告警通道由架构确定。

### SM-7 Linux 交付

Go 服务通过可复现构建与打包命令部署到确定的 Linux 环境，由 systemd 管理。对应 NFR-6，技术约束见 addendum。

### SM-8 扩展与密钥管理

新增平台适配器不改变核心关系模型，生产支持专用密钥管理服务。对应 NFR-4、NFR-6，后端由架构确定。

**不可放宽的约束**：

- **SM-C1 凭据泄漏**：检查源码、Git、日志、测试数据、审计、告警和错误响应，任何真实凭据泄漏均不满足 NFR-1；获授权正常查询的明文输出不属于错误或日志。
- **SM-C2 错误归属与越权**：便利性不能通过混用安装授权、破坏唯一映射或允许无权限调用者取密实现，见 FR-2、FR-3、FR-4、FR-11。

PRD 不虚构延迟、吞吐、可用性、恢复时限或效率提升数值；必要运行质量目标由架构按 Q-9 落实，衡量便利性时同时检查泄漏、错误归属和越权。
