# 结论

**当前：PASS，无未解决发现。** 以下首次审查发现保留为历史；2026-10-08 修订复核已确认 H-1/H-2/H-3/M-1 及推荐清单 R-5 对齐全部解决，具体证据见文末。

按 `reviewer-gate.md` good-spine checklist 审查当前 [ARCHITECTURE-SPINE.md](../ARCHITECTURE-SPINE.md)，并交叉读取技术依据；未编辑架构正文，未做平台联调或 Linux 权限实测。

## 高优先级

### H-1 — Socket 创建职责与已定权限冲突（AD-3:61，AD-14:127）

目录固定为 `root:hub-clients 0750`，服务又固定非 root `hubd`，因此 hubd 不能在目录创建或重建 pathname Socket。当前未决定由 systemd socket activation 创建并传入 listener；部署者可分别采用 root helper、提高目录组写权限或修改服务账户，导致安全边界分叉。

**处理：autofix。** 明确采用 systemd 创建 Socket 并传递 fd，或采用仅 hubd 可写、客户端仅可遍历的目录方案；在 AD-3/AD-14 统一创建、重启清理及 ownership 职责。精确 unit 语法可留部署 Story，但 listener 的创建模型必须现在固定。验证普通客户端不能替换/删除 Socket，非 root 服务重启可恢复监听。

### H-2 — 刷新和授权兑换的排他边界不统一（AD-9:97，AD-10:103）

AD-9 限制同安装一个“维护操作”，AD-10 的单飞与唯一性则属于 session/operation；未要求同一安装的重新授权兑换与后台刷新共享排他/栅栏。两位实现者可分别建立锁而同时对平台操作。generation CAS 只防本地旧结果覆盖，不能阻止两次远端操作互相轮换或撤销对方 Token。授权返回多个店铺时还可能直到响应才知道安装身份。

**处理：autofix＋provider Story 前细化。** 将所有可能改变远端凭据的授权、刷新纳入一个 application 所有的排他协调契约；身份尚未知时规定保守的 App 级范围，已核实平台契约允许时再缩小。AD-10 引用 AD-9 的统一领取/终结/结果不确定规则，不独立发明锁。平台资料确定实际冲突域，但不能让两个模块先各自实现。测试重新授权与刷新并发、一个回调关联多个安装和迟到结果。

### H-3 — 平台成功之后的加密/落库失败缺少终结规则（AD-6:79，AD-9:97，AD-10:103）

文本规定“结果先加密保存再条件提交”，但 `indeterminate` 只明确覆盖超时/进程中断。平台已经成功轮换，随后 KMS 加密失败、DB 写失败或提交失败时，新 Token 无法持久恢复；原 Token 可能已失效。单纯按 AD-6 失败不替换旧记录虽保证本地事务，却不能说明任务是否再次轮换、该旧值是否仍视为已确认可用。不同实现可能立即重试平台、清除 operation 或继续宣称旧值有效。

**处理：autofix。** 明确领取记录在安全终结前不会释放；任何可能已发生远端副作用、且新结果未可靠保存的失败都进入未决恢复流程，禁止盲目平台重放。能够安全持久化的加密结果只重试本地条件提交；无法保存的结果按平台契约复核/重新授权，并依据轮换契约更新旧值有效性证据，不把 KMS 故障本身当平台失效。补充 post-success KMS/DB 故障注入验收。

## 中优先级

### M-1 — 请求管理资格和延迟变更的授权线性化点未定义（AD-3:61，AD-5:73）

返回明文前的政策复核明确；长请求在等待平台期间 manage 被撤销后能否提交、本来由该账户发起的尚未消费授权会话能否继续兑换则未说明。请求开始授权和提交前重核都可形成一致策略，但必须选定，避免 CLI/回调各自解释“撤销无需重启”。

**处理：autofix 或加入有负责人、Story 前必须决定的 Deferred 条目。** 规定管理变更的授权生效点与会话账户撤销语义；若已发起远端调用，仍完成安全结果保存/审计，不以本地权限撤销为由丢弃不可重放的轮换结果。测试权限在平台响应前撤销。
