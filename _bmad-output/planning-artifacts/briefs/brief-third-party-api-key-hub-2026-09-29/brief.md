# 产品简报：第三方平台 API 凭据管理中心

## 执行摘要

本项目面向内部系统，建设一个统一的第三方平台接入与 API 凭据管理中心。系统围绕平台 App、外部平台店铺、品牌和内部系统店铺建立稳定关联，负责第三方授权凭据的获取、保存、刷新、撤销和查询。

第一阶段聚焦首批接入平台中的一个平台，覆盖其授权回调、凭据生命周期和店铺归属映射。长期目标是让内部系统通过统一的品牌或店铺身份获得第三方平台连接能力，而不必分别实现各个平台的授权回调、Token 生命周期和凭据映射。

## 问题

第三方平台的凭据通常产生于平台 App 的安装授权过程，而不是一个孤立的 API Key。当前需要同时处理以下关系：一个 App 可以安装到多个外部店铺，一个外部店铺可以安装多个 App，一个外部店铺只能属于一个品牌，一个品牌与内部系统店铺保持双向一对一关系。

如果这些关系和凭据分散在各个平台控制台、环境变量或业务代码中，内部系统难以判断某个凭据对应哪个店铺和品牌，也难以统一处理授权过期、Token 刷新、撤销、审计和新增平台接入。

## 服务对象

### 集成运维人员

负责登记平台 App、发起店铺授权、处理失效授权和维护品牌及内部店铺映射。他们需要清晰查看授权状态、失效时间和归属关系。

### 内部业务系统和自动化脚本

通过统一接口或 CLI 获取指定品牌、内部店铺或外部店铺对应的可用凭据信息，并调用第三方 API。

### 终端用户

后续可能直接在自己的终端安装 CLI 查询授权状态或凭据信息，因此 CLI 需要较少的依赖项、稳定的退出码、稳定的 JSON 输出和明确的敏感字段控制。

## 已确认约束

- 项目使用 Go 构建，服务和 CLI 共用平台适配器、授权状态及凭据管理核心。
- Linux 部署不绑定单一安装包格式，提供可复现的构建与打包命令；常驻服务支持 `systemd`。
- CLI 以 JSON-first 的稳定机器可读格式为主，适合 AI 和脚本解析，并支持后续独立分发到用户终端。
- 真实凭据不得进入源码、Git、日志或未授权错误响应；生产环境需要预留专用密钥管理服务。

## 待确认决策

- [ASSUMPTION] 首批平台是 TikTok 相关平台，但需要明确是 TikTok Shop、TikTok Ads 还是其他产品线。
- [ASSUMPTION] 首期授权方式以 OAuth 为主，是否支持手工 API Key 导入待确认。
- [ASSUMPTION] CLI 的 JSON 输出包含平台、App、外部店铺、品牌、内部店铺、凭据类型、状态和有效期；是否允许输出完整 Token，需要明确权限和显式参数规则。
- 生产环境的密钥管理服务、目标部署发行版和 CLI 终端分发渠道待确认。

## 解决方案

系统以安装授权作为 App 与外部店铺之间的核心关联：

```text
第三方平台
  └─ 平台 App
      └─ Installation / Authorization
          └─ 外部平台店铺
```

关系约束如下：

- 平台 App 与外部平台店铺是多对多关系，通过安装授权关联。
- 外部平台店铺与品牌是多对一关系，一个外部店铺只能属于一个品牌。
- 品牌与内部系统店铺是双向一对一关系。

核心能力包括：

- 登记第三方平台和平台 App。
- 发起店铺安装或 OAuth 授权，并接收回调。
- 管理 App 级凭据和安装授权产生的店铺级凭据。
- 保存、验证、刷新、撤销和查询凭据状态。
- 维护外部店铺、品牌和内部系统店铺映射。
- 通过平台适配器隔离 TikTok 等平台的授权和 API 差异。
- 由 Go 服务承接回调，由 JSON-first CLI 输出机器可读的可用凭据信息。

设计重点如下：

- 以“安装授权”而非单个 API Key 作为凭据管理核心，能正确表达 App 与店铺的多对多关系。
- 将第三方店铺归属和内部店铺归属纳入凭据查询链路，减少业务系统自行拼接映射的需要。
- 服务和 CLI 共用同一套核心模型，既支持 Linux 常驻服务，也支持后续把 CLI 独立分发到用户终端。
- Go 的编译产物可以通过统一命令生成面向不同 Linux 目标的安装包或分发包，不绑定单一打包格式。

## 范围

### 第一阶段包含

- 第三方平台、平台 App、外部店铺、品牌、内部店铺和安装授权的领域模型。
- 首批接入平台中的一个平台的完整授权回调流程。具体 TikTok 产品线待确认。
- App 级和店铺安装级凭据的生命周期管理。
- 外部店铺到品牌、品牌到内部店铺的映射和唯一性校验。
- Go 编写的 Linux 服务、`systemd` 服务配置和可复现的构建/打包命令。
- JSON-first CLI 查询能力及基础访问审计。

### 后续阶段

- 更多平台适配器。
- 更丰富的凭据代理调用能力。
- 多租户、角色权限和更细粒度的终端授权策略。
- 商品、订单、广告等第三方业务数据同步。

## 成功标准

- 新增一个平台适配器时，不需要修改核心的店铺、品牌、内部店铺和安装授权模型。
- 一个 App 可以管理多个外部店铺，一个外部店铺可以管理多个 App，且每个安装授权的凭据状态独立可追踪。
- 每个外部店铺只能关联一个品牌，每个品牌与一个内部系统店铺保持双向唯一关系。
- 授权回调可安全、幂等地完成凭据保存和关联关系更新。
- CLI 默认输出稳定、机器可读的 JSON，可按业务归属查询可直接用于调用 API 的凭据信息。
- 凭据不进入源码、Git、日志或未授权错误响应；生产环境支持专用密钥管理服务。
- Go 服务可以通过构建和打包命令部署到 Linux，并由 `systemd` 管理运行。
