## PM-01 — 恢复资格不能仅由 generation 大小证明

**依据**：架构 AD-7（L85）规定只有晚于停用版本的重新授权／显式替换才能恢复；版本约定（L137）又规定刷新也会推进 generation。Story 1.18（L859–867）要求刷新不能构成恢复依据，Story 2.7（L1138–1141）明确刷新推进版本但保持停用。

**反例**：generation=5 时停用，disabled_generation=5；后台刷新产生 generation=6，仍 disabled。此时运维调用 restore。若实现只验证 generation > disabled_generation、当前有效性、映射和 manage，刷新出的版本也能通过，违反“必须先重新授权或明确替换”的前置条件。文档的业务意图明确，但列出的持久化状态不足以单独证明该意图已经发生。依赖操作审计推断也不可靠，因为审计允许写入失败和缺口。

**建议**：在领域契约中定义可事务保存的恢复资格证据，例如停用之后最近一次合格替换／重新授权的版本及 operation 引用，或者等价的来源与状态转换证明。具体字段名可由设计选择。明确替换后又刷新、再次停用、重启和恢复快照时证据如何保留或失效，不能只检查版本递增。

**验收补充**：停用→仅刷新→显式 restore 必须拒绝；停用→明确替换→显式 restore 在其他条件满足时成功；两条路径重启后保持相同结果。再覆盖“替换后刷新”和“再次停用”以固定资格沿革。

**判断边界**：高置信度的状态模型细化缺口，不断言遵守全部业务规则的实现一定会绕过停用。应扩展架构 AD-7／版本约定和对应 Story，保留已接受的恢复原则。

## PM-02 — 秘密换代后，确认与验证证据的有效范围未固定

**依据**：PRD FR-6（L156、L166）要求手工导入的未知有效期凭据经运维确认后才可取密；FR-7（L179）要求验证结果归属于对应凭据。架构 AD-7（L85）列出 confirmed_by_operator、validation_result 和 generation，却没有给出换代时这些证据的转换规则。Story 1.13（L679–687）规定替换推进版本、保留停用状态，未说明旧确认／验证结果的处理；Story 1.15（L745–753）定义确认和可用性，却未覆盖确认后替换；Story 2.6（L1107–1108）只处理异步验证响应的版本冲突。

**反例**：虚构值 A、未知有效期、运维已确认可用。随后显式替换成虚构值 B，导入请求没有确认 B。若保留旧 confirmed_by_operator=true，B 可以直接继承 A 的可用证据；若所有更新都重置确认，则经过平台成功兑换或刷新取得的值又需要另一套明确的可用性规则。两个实现都可能通过现有分散的验收场景。

**建议**：增加按“首次导入／替换／重新授权／刷新／确认／验证”列出的状态转换表，固定每种事件如何设置有效期、确认和验证证据。证据应绑定其适用秘密版本，或者通过等价的强制重置规则保证不能误继承；平台兑换／刷新如何证明新值可用也需独立定义。

**验收补充**：A 已确认→替换 B 未确认，不能仅凭 A 的确认允许 B 取密；B 在同次导入显式确认或随后确认的行为明确。旧 generation 的验证结果不得证明新值已验证，平台新值按其已核实 profile 的规则判定可用。

**判断边界**：高置信度的转换规则缺口；目前没有代码，不能认定旧证据已经被错误继承。

## PM-03 — 区分业务失效报告与运维主动停用

**依据**：PRD FR-7（L185）要求业务发现失效后通过本地 CLI 标记目标失效；Story 1.18（L850、L854–857）将 disable／mark-invalid／restore 列为用例，但失效标记验收没有要求调用者携带其使用的凭据版本。AD-5 的服务端 CAS 保护的是操作快照之后的并发变化，不能自动识别命令发起之前业务调用使用的是旧值。

**反例**：脚本取得 generation=10 的 Token A；后台刷新提交 generation=11 的 Token B；脚本收到 A 的失效响应后调用 mark-invalid，命令只指定 App／安装／type。服务读取当前 generation=11 并成功 CAS 停用 B。请求执行期间没有冲突，普通 CAS 完全通过，却把未被该业务响应证明失效的新值停用了。

**建议**：业务失效报告携带所用 generation 或等价非敏感版本引用，服务只对匹配版本应用该证据；不匹配时按稳定契约返回安全冲突。运维有意主动停用当前目标可保持独立命令语义。查询响应如何提供该版本引用，应在 SQ-2 契约中决定。

**验收补充**：旧值查询→刷新成功→旧值失效上报，新值不被停用；当前值的明确失效报告可以停用；运维主动 disable 仍可停用当前值。返回与审计只记录版本引用，不传回 Token 作为比对材料。

**判断边界**：高置信度的并发交互缺口。若最终设计选择“失效报告就是无条件主动停用”，需明确承认该操作含义与其对新值的影响，不能把它描述成仅标记已证实失效的值。

## PM-04 — 同主版本可选扩展会被旧 CLI 拒绝

**依据**：PRD FR-10（L246）和 NFR-5（L303）允许同主版本增加兼容的可选字段；架构 AD-13（L121）及 Story 1.1（L233）承接这一要求。Story 1.16（L798–801）却把服务响应“额外字段”与截断、畸形、超时一并列为必须安全拒绝的场景；架构输入／输出约定（L140）也未区分两端的未知字段策略。

**反例**：hubd v1 增加一个可选非敏感响应字段，旧 hub v1 按额外字段拒绝整个结果。既有字段、类型和含义完全没变，现有脚本仍然失败，违反同主版本兼容承诺。

**建议**：分别定义请求和响应策略。请求可继续拒绝未知／重复字段；响应须明确允许扩展的位置与旧客户端处理方式。可选择允许可选元数据扩展并忽略未知字段，但只输出已验证的业务凭据白名单；未知秘密 type、重复凭据项、类型错误、错误对象夹带秘密仍拒绝。另一条路径是协商响应能力，但需证明它维持已接受的同主版本兼容。

**验收补充**：旧 CLI＋新增合法可选字段的服务成功；旧 CLI＋既有字段改变类型失败；重复项、错误响应夹带秘密和未允许的凭据扩展失败。修订 Story 1.16 的“额外字段”措辞，使其准确指向违反扩展策略的字段。

**判断边界**：高置信度的直接文档冲突，不依赖平台协议或运行环境。

## PM-05 — SQ-3 待处置结果保护的产出者不明确

**依据**：Story 2.4 的 Gates（L1008）要求 SQ-3“受保护待处置结果”；Story 2.5（L1051）要求加密结果保存契约，2.7（L1127）要求持久化结果。前置设计 1.2（L252–259）定义的是当前凭据目标／type／generation 密文包，L276–279 只定义平台失败的恢复交接规则；1.6（L419–441）验证当前密文交换、旧版本解密和身份生命周期。实施门槛表的 SQ-3 也没有明确待处置结果包的独立产出与验收项。

**缺口**：待处置平台结果在当前领域值尚未提交时需要保护，可能包含多个店铺和业务／管理秘密。其绑定对象、operation／App／epoch／预期版本、防跨操作交换、允许的解密消费者及最终转成当前凭据的规则不能直接由“当前凭据目标＋type＋generation”推出。计划设置了门槛，但没有明确哪项前序产物证明这个子门槛已满足；仅把 1.2／1.6 标完成仍不足以证明 2.4 可以派发。

**建议**：扩展 1.2／1.6 的设计与验证范围，或在 2.4 之前增加独立的结果保护契约任务。固定结果包绑定和状态转换、重启后的本地提交校验、过时快照处理及不含秘密的处置入口；更新 SQ-3 子项与追溯。只重试本地条件提交、禁止盲目重放平台请求的原则保持不变。

**验收补充**：App A／operation X 的加密待处置包不能被 operation Y 或 App B 使用；结果保存后崩溃可恢复检查；epoch／CAS 过时或权限撤销时不能提交；未能加密保存时不落明文。设计与隔离实证分别有明确产物和通过依据。

**判断边界**：中高置信度的任务交接缺口。AD-9 已规定安全行为，本问题不是缺少 indeterminate 原则，而是缺少实现之前可引用的保护契约产出者。

## PM-06 — README 没有给出当前文档入口

**依据**：README 的当前状态（L5–10）仅列初始化和 BMAD 安装，开始使用（L12–16）建议运行 bmad-help；没有指向当前 SPEC、实施门槛或 CE 开发就绪判断。docs/project-brief.md 仍保留首批平台和后端待确认项；PRD／SPEC 解释了旧材料的优先级，但从项目首页看不到这条路由。

**影响**：新接手者或工具容易优先读取旧简报，重复询问已经决定的 TikTok／OpenBao／本地 CLI 选择，或将 final 文档状态误解成实施就绪。现行文档已有正确答案，缺的是入口。

**建议**：README 增加精简的“现行契约／当前阶段”入口，链接 SPEC、companions、implementation-gates 和 CE-VALIDATION；明确已完成规划、尚未实施。早期简报标明其历史输入角色并链接现行入口即可，不重写历史内容。

**验收补充**：只从 README 出发即可定位现行产品／架构基线和未完成实施门槛；不把文档 final 写成实现或联调通过。

**判断边界**：高置信度的入口问题，优先级低于领域与协议契约。
