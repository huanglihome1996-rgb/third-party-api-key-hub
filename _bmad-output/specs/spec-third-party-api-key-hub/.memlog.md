- (note) Why: 内部运维和业务脚本需要按统一品牌或店铺身份取得第三方 API 凭据，避免各系统重复处理授权、生命周期与归属映射。首期接入 TikTok Shop，在服务所在 Linux 主机提供 CLI 管理与取密，使调用者取得归属正确、当前可用且完整的业务调用凭据。
- (capability) CAP-1 = FR-1; intent: 登记平台与 App，供安装授权和凭据引用。 success: TikTok Shop App 可登记并被关联；缺少平台、中心 App ID、平台 App ID 或违反唯一性时整笔拒绝，原记录不变。 细项验收采用 PRD FR-1 与架构规则。
- (capability) CAP-2 = FR-2; intent: 维护 App 与外部店铺的安装授权关联，并分别检查状态。 success: 至少两个 App 与两个外部店铺的多对多关联可独立追踪；同一组合再次授权只更新当前授权，不产生供取密选择的旧版本。 细项验收采用 PRD FR-2 与架构规则。
- (capability) CAP-3 = FR-3; intent: 维护外部店铺所属品牌，使凭据可按品牌定位。 success: 外部店铺只属一个品牌，品牌可有多个外部店铺；冲突整笔拒绝，解除或变更立即影响取密，缺链时无明文。 细项验收采用 PRD FR-3 与架构规则。
- (capability) CAP-4 = FR-4; intent: 维护品牌与内部店铺的映射，使两端定位同一归属。 success: 双向一对一成立；唯一性冲突不改原映射，变更后旧归属不可取密，完整链缺失时全部查询路径拒绝明文。 细项验收采用 PRD FR-4 与架构规则。
- (capability) CAP-5 = FR-5; intent: 发起 TikTok Shop 店铺授权并检查取得的凭据与安装归属。 success: CLI 发起、平台页面同意、服务回调、CLI 查结果的流程可完成；安全校验失败不保存，重复不新增当前授权，再次授权失败不误报更新，也不解除本地停用。 细项验收采用 PRD FR-5 与架构规则。
- (capability) CAP-6 = FR-6; intent: 手工导入 App 级或店铺级 API Key／Token，并明确确认可用性。 success: 隐藏交互与 stdin 均可导入且不回显或回传输入值；归属、类型、值必填，已有同类型须显式替换；未知有效期经运维确认可用且明确标未知，平台验证可选。 细项验收采用 PRD FR-6 与架构规则。
- (capability) CAP-7 = FR-7; intent: 保存并检查凭据状态、有效期和验证结果，标记明确失效。 success: App 与安装凭据可独立追踪；运维确认与平台验证可区分，暂时验证故障保持原可用性而不恢复不可用值；明确失效可本地标记并停用，过期和停用值无明文。 细项验收采用 PRD FR-7 与架构规则。
- (capability) CAP-8 = FR-8; intent: 自动维护支持刷新的凭据，并本地停用或显式恢复目标凭据。 success: 刷新成功更新当前值；失败不延长有效期，仍有效且未停用的旧值可返回；本地停用立即拒绝取密，刷新／验证／映射恢复不解除；重新授权或显式替换后仍须显式恢复。 细项验收采用 PRD FR-8 与架构规则。
- (capability) CAP-9 = FR-9; intent: 按品牌、内部店铺或外部店铺取得对应的完整业务调用凭据。 success: 唯一 App／店铺自动解析，多项要求指定；完整归属且有权限时返回所选 App 调用凭据与店铺 Token，不含管理／刷新专用值；任一必需项不可用则整体无明文，不提供独立 App 取密路径。 细项验收采用 PRD FR-9 与架构规则。
- (capability) CAP-10 = FR-10; intent: 用稳定、机器可读的结果接入业务脚本。 success: 成功查询 JSON 含 identity、credentials、status 三组及完整业务凭据、全部归属标识和各类型的状态／有效期；失败仅 error/message 且无秘密，stdout 只含 JSON、诊断在 stderr，退出码成功 0／失败 1，同主版本兼容。 细项验收采用 PRD FR-10 与架构规则。
- (capability) CAP-11 = FR-11; intent: 按受控 Linux 账户资格限定本地主机管理与取密。 success: 获 read 资格的账户可在服务主机取密，变更须 manage；未授权账户及其他主机不能取密且不获越权对象信息，公开回调不扩大权限，资格撤销按架构即时复核。 细项验收采用 PRD FR-11 与架构规则。
- (capability) CAP-12 = FR-12; intent: 检索凭据相关成功与失败操作的非敏感审计记录。 success: 审计含时间、Linux 账户、操作、非敏感目标、结果、错误类别和操作 ID，至少保留一年；范围覆盖凭据操作、App 登记、映射及入口拒绝，检索受 manage 限制；写入失败不阻断原操作且有安全告警，缺口不伪装已记录。 细项验收采用 PRD FR-12 与架构规则。
- (constraint) 首期范围为 FR-1 至 FR-12；产品验收以 adopted PRD 为准，架构 AD-1 至 AD-14、版本约定和运行目标均已采用。原 PRD/addendum 的技术“待设计”是架构前交接状态，现状按 implementation-gates.md 路由，不重开已接受选择。
- (constraint) Go 六边形模块化单体，单节点单实例 hubd 执行业务规则，hub 是本地 CLI；应用用例唯一变更入口，平台适配器隔离差异，新增平台不得改变核心关系模型。
- (constraint) 取密只经服务主机 Unix Socket 和内核身份授权；业务/审计库、密钥后端和管理操作不能由 CLI 绕过。公开入口仅回调，不开放远程管理或取密。
- (constraint) 生产使用 OpenBao Transit，SQLite 仅存密文与元数据，无明文降级或跨请求秘密缓存；真实凭据禁止进入源码、Git、日志、测试、审计、告警和错误，受权正常取密按完整结果输出。
- (constraint) 关系唯一性、完整映射、当前值版本、状态 CAS、App 级授权／刷新协调与外部结果不确定的恢复须遵守架构；不得盲目重放可能已生效的平台调用，不输出部分凭据。
- (constraint) 所有命令使用共同 contract/v1；导入不接受秘密命令参数，stdin 缺项不进入交互等待。平台能力与字段用途须由已核实 profile 定义，不能从通用 OAuth 或其他身份接口推定 Seller 事实。
- (constraint) 可复现 Linux 构建／打包与 systemd，验收 Ubuntu 24.04 LTS、linux/amd64 和 linux/arm64；依赖版本按架构锁定。10 个本地并发、健康 KMS 下取密 p95 ≤2s、每日一致备份、RPO ≤24h、人工恢复 RTO ≤4h 是目标，仍须实测。
- (constraint) Non-goal: 首期不建设 Web 管理界面、远程取密、独立终端分发、钉钉认证、对象级权限／多租户／多节点、其他平台、业务 API 代理或商品／订单／广告数据同步。
- (constraint) Non-goal: 不自动撤销第三方平台授权；Vaultwarden 密钥更新推送和其平台内查看权限属于后续方向，不替代首期 OpenBao 或 Linux CLI 授权，不加入首期验收。
